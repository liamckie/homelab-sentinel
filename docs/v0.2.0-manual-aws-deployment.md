# V0.2.0 Manual AWS Deployment

## Objective

Manually deploy Homelab Sentinel to AWS to understand Amazon ECR, ECS Fargate, IAM, VPC networking and CloudWatch before recreating the infrastructure with Terraform.

## Scope

### Included
- AWS account preparation and cost controls
- Temporary CLI authentication
- Private ECR repository and basic image scanning
- Manual ECS Fargate deployment
- CloudWatch logging
- Direct task connectivity testing
- ECS recovery testing
- Connectivity troubleshooting
- Resource cleanup

### Excluded
- Terraform
- Application Load Balancer
- Custom VPC and NAT Gateway
- ACM and DNS
- GitHub Actions and OIDC
- DynamoDB and heartbeat alerting
- Automated missed-heartbeat alerting
- Production hardening

## Account Preparation

- Enabled root-account MFA.
- Created a separate MFA-protected IAM administrator.
- Created a recurring $10 monthly budget.
- Selected eu-west-2.
- Installed AWS CLI v2 in the development Proxmox LXC.
- Configured temporary browser-based authentication.
- Confirmed the CLI returned the IAM administrator ARN rather than root.

## Deployment Steps

### 1. AWS account preparation

Prepared the AWS account before creating application infrastructure. This included securing the root account, creating a separate IAM administrator, configuring cost alerts and verifying temporary AWS CLI authentication.

See the Account Preparation section for the completed controls.

### 2. Reusable shell variables

These variables apply only to the current shell session. They must be exported
again in a new terminal session. `AWS_PROFILE` contains an AWS CLI profile
name; it is not necessarily the IAM username.

```bash
export AWS_PROFILE="<aws-profile-name>"
export AWS_REGION="eu-west-2"
export AWS_PAGER=""

export ECR_REPOSITORY_NAME="homelab-sentinel"
export ECR_IMAGE_TAG="v0.2.0-amd64-r2"
export CONTAINER_PLATFORM="linux/amd64"

export ECS_CLUSTER_NAME="homelab-sentinel-cluster"
export ECS_SERVICE_NAME="homelab-sentinel-service-62kc5h66"
export ECS_TASK_DEFINITION_FAMILY="homelab-sentinel"
export CLOUDWATCH_LOG_GROUP="/ecs/homelab-sentinel"
```

Verify the active identity and Region before creating resources:

```bash
aws sts get-caller-identity \
  --query 'Arn' \
  --output text \
  --no-cli-pager

aws configure get region
```

The ARN must identify the administrator and must not end in `:root`.

### 3. ECR repository and container image

Created the private `homelab-sentinel` ECR repository in `eu-west-2` with:

- Private visibility
- Immutable image tags
- Basic scanning on push
- AES-256 encryption using an AWS-owned key

Verify these values against the original repository configuration before
copying them into the final document.

Retrieve the repository URI and registry hostname:

```bash
export ECR_REPOSITORY_URI="$(
  aws ecr describe-repositories \
    --repository-names "$ECR_REPOSITORY_NAME" \
    --query 'repositories[0].repositoryUri' \
    --output text \
    --no-cli-pager
)"

export ECR_REGISTRY="${ECR_REPOSITORY_URI%%/*}"
```

Authenticate Docker to ECR without storing the temporary ECR password in the
documentation:

```bash
aws ecr get-login-password |
docker login \
  --username AWS \
  --password-stdin "$ECR_REGISTRY"
```

Build and push a single-platform image. Provenance and SBOM attestations were
disabled for this version so that the tag referenced a scannable image manifest
rather than an OCI image index:

```bash
docker buildx build \
  --platform "$CONTAINER_PLATFORM" \
  --provenance=false \
  --sbom=false \
  --tag "$ECR_REPOSITORY_URI:$ECR_IMAGE_TAG" \
  --push \
  .
```

The final image used by ECS was tagged `v0.2.0-amd64-r2`. The image was
verified through both the ECR console and AWS CLI, and the completed basic scan
was retrieved before deployment.

### 4. CloudWatch and IAM

Created the CloudWatch log group `/ecs/homelab-sentinel` with seven-day log
retention.

Created an ECS task execution role and attached only the AWS-managed
`AmazonECSTaskExecutionRolePolicy`. This allowed the ECS agent to retrieve the
image from ECR and send container logs to CloudWatch.

No application task role was required because V0.2.0 did not make AWS API
calls from the Sentinel application.

### 6. ECS cluster, service and networking

Created the `homelab-sentinel-cluster` ECS cluster and a Fargate service with a
desired count of one.

For this short-lived learning deployment, the task used:

- The default VPC
- A public subnet with a route to an internet gateway
- A public IPv4 address assigned to the task ENI
- A Sentinel-specific security group
- Inbound TCP port 8000 restricted to the administrator's current public IPv4
  address using a `/32` rule
- Default outbound access so the task could pull its image and send logs

The application was reached directly over HTTP using the temporary task public
IP. This was acceptable only for the time-boxed learning spike because TLS,
authentication and a stable load-balanced endpoint were explicitly outside
the scope of V0.2.0.

### 7. Application and logging validation

Retrieved the running task through the exact console-generated service name:

```bash
export ECS_TASK_ARN="$(
  aws ecs list-tasks \
    --cluster "$ECS_CLUSTER_NAME" \
    --service-name "$ECS_SERVICE_NAME" \
    --desired-status RUNNING \
    --query 'taskArns[0]' \
    --output text \
    --no-cli-pager
)"
```

Verified that the task was running and healthy:

```bash
aws ecs describe-tasks \
  --cluster "$ECS_CLUSTER_NAME" \
  --tasks "$ECS_TASK_ARN" \
  --query 'tasks[0].{
    LastStatus:lastStatus,
    DesiredStatus:desiredStatus,
    HealthStatus:healthStatus
  }' \
  --output table \
  --no-cli-pager
```

Retrieved the task ENI and temporary public IP:

```bash
export ECS_ENI_ID="$(
  aws ecs describe-tasks \
    --cluster "$ECS_CLUSTER_NAME" \
    --tasks "$ECS_TASK_ARN" \
    --query 'tasks[0].attachments[0].details[?name==`networkInterfaceId`].value | [0]' \
    --output text \
    --no-cli-pager
)"

export ECS_PUBLIC_IP="$(
  aws ec2 describe-network-interfaces \
    --network-interface-ids "$ECS_ENI_ID" \
    --query 'NetworkInterfaces[0].Association.PublicIp' \
    --output text \
    --no-cli-pager
)"
```

Validated the application endpoints:

```bash
curl -i --connect-timeout 5 --max-time 10 \
  "http://${ECS_PUBLIC_IP}:8000/health"

curl -i --connect-timeout 5 --max-time 10 \
  -X POST "http://${ECS_PUBLIC_IP}:8000/heartbeat"

curl -fsS --connect-timeout 5 --max-time 10 \
  "http://${ECS_PUBLIC_IP}:8000/api/status" |
python3 -m json.tool

curl -i --connect-timeout 5 --max-time 10 \
  "http://${ECS_PUBLIC_IP}:8000/status"
```

Confirmed that the external requests appeared in CloudWatch:

```bash
aws logs tail "$CLOUDWATCH_LOG_GROUP" \
  --since 15m \
  --format short \
  --no-cli-pager
```

### 8. ECS recovery test

The running task was deliberately stopped while the ECS service retained a
desired count of one.

```bash
export OLD_ECS_TASK_ARN="$ECS_TASK_ARN"
export OLD_ECS_ENI_ID="$ECS_ENI_ID"
export OLD_ECS_PUBLIC_IP="$ECS_PUBLIC_IP"

aws ecs stop-task \
  --cluster "$ECS_CLUSTER_NAME" \
  --task "$OLD_ECS_TASK_ARN" \
  --reason "Manual ECS service recovery test for V0.2.0" \
  --no-cli-pager

aws ecs wait tasks-stopped \
  --cluster "$ECS_CLUSTER_NAME" \
  --tasks "$OLD_ECS_TASK_ARN"

aws ecs wait services-stable \
  --cluster "$ECS_CLUSTER_NAME" \
  --services "$ECS_SERVICE_NAME"
```

AWS CLI waiter commands normally produce no output when they succeed. The
replacement task was then retrieved and compared with the original task.

| Validation | Result |
|---|---|
| Original task stopped | Passed |
| Stop reason recorded | Passed |
| Replacement task created | Passed |
| Replacement task ARN differed | Passed |
| Replacement reached `RUNNING` | Passed |
| Replacement became `HEALTHY` | Passed |
| Service returned to desired count | 1 desired, 1 running, 0 pending |
| Replacement `/health` request | `200 OK` |
| Replacement public IP changed | Confirmed |
| Previous heartbeat state retained | No; state was held in container memory |
| Replacement logs in CloudWatch | Confirmed |

The ECS service reconciled actual state with its desired count. Stopping the
running task reduced the service below its desired count, so ECS provisioned a
new task rather than restarting the original task.

The replacement received a new task ARN, ENI and public IP. This demonstrates
why clients should not depend on the address of an individual Fargate task. A
later deployment will use an Application Load Balancer to provide a stable
endpoint.

The previously received heartbeat was not retained because V0.2.0 stored state
in application memory. A later version will use DynamoDB so heartbeat state can
survive task replacement.

## Problems and Resolutions

### AWS CLI installation failed with package 404 errors

**Status:** Resolved

**Symptom**

Installing `awscli` through APT failed because Ubuntu attempted to download package versions that were no longer available from the configured repository.

**Cause**

The LXC had stale APT package information, and the Ubuntu repository package did not provide the required current AWS CLI v2 installation.

**Resolution**

Refreshed the package information, repaired the incomplete package operation and installed AWS CLI v2 using the official AWS installer.

**Recovery commands**

```bash
sudo apt update
sudo apt --fix-broken install
```

AWS CLI v2 was then installed using the official AWS installation procedure.

**Verification**

```bash
aws --version
```

The command returned AWS CLI version 2 successfully.

### AWS CLI authenticated as the root user

**Status:** Resolved

**Symptom**

`aws sts get-caller-identity` returned an ARN ending in `:root`.

**Cause**

The browser authentication session had been completed using the AWS root account rather than the separate IAM administrator.

**Resolution**

Logged out of the cached CLI session and authenticated again using the MFA-protected IAM administrator.

**Recovery commands**

```bash
aws logout 
aws login --remote 
```

**Verification**

```bash
aws sts get-caller-identity 
```

The returned ARN identified the IAM administrator and did not end in `:root`. The actual account ID and administrator name have been omitted from this document.

### ECR could not scan the original OCI image index

**Status:** Resolved

**Symptom**

Attempting to scan the original `v0.2.0` image returned:

```text
UnsupportedImageTypeException:
An artifact with media type
'application/vnd.oci.image.index.v1+json' cannot be scanned.
```

**Cause**

Docker Buildx had included a provenance attestation. The runnable image manifest and its provenance attestation were stored beneath an OCI image index, which ECR displayed as the tagged index and two additional untagged artifacts.

ECR could store these OCI artifacts, but ECR basic scanning could not scan the parent image index.

**Resolution**

Built and pushed a single-platform `linux/amd64` image with provenance and SBOM attestations disabled. The corrected image was tagged `` to avoid overwriting the original immutable tag.

**Recovery commands**

```bash
ECR_REPOSITORY_URI=$(aws ecr describe-repositories \
  --repository-names $ECR_REPOSITORY_NAME \
  --query 'repositories[0].repositoryUri' \
  --output text)
```

```bash
ECR_REGISTRY="${ECR_REPOSITORY_URI%%/*}"

aws ecr get-login-password \
docker login \
  --username AWS \
  --password-stdin "$ECR_REGISTRY"
```

```bash
docker buildx build \
  --platform linux/amd64 \
  --provenance=false \
  --sbom=false \
  --tag "$ECR_REPOSITORY_URI:$ECR_IMAGE_TAG" \
  --push \
  .
```

**Verification**

```bash
aws ecr describe-images \
  --image-ids imageTag=$ECR_IMAGE_TAG \
  --query 'imageDetails[0].imageManifestMediaType' \
  --output text
```

The new tag referenced a single image manifest rather than an OCI image index.

### Manual scan request reached the ECR scan quota

**Status:** Resolved

**Symptom**

Starting a manual scan for `` returned a scan-quota error.

**Cause**

A vulnerability scan had already completed for the image. ECR permits one basic scan per individual image within a 24-hour period, including a scan initiated when an image is pushed.

**Resolution**

Retrieved the existing scan rather than attempting to start another scan.

**Recovery and verification command**

```bash
aws ecr describe-image-scan-findings \
  --image-id imageTag=$ECR_IMAGE_TAG \
  --query '{
    Status:imageScanStatus.status,
    Description:imageScanStatus.description,
    Findings:imageScanFindings.findingSeverityCounts
  }' \
  --output json
```

The returned status was `COMPLETE`, confirming that the scan had completed successfully.

**Cause**

**Investigation command**

```bash
aws ecr describe-image-scan-findings \
  --image-id imageTag=$ECR_IMAGE_TAG \
  --max-items 1000 \
  --query 'imageScanFindings.findings[].{Severity:severity,CVE:name,Package:attributes[?key==`package_name`].value | [0],InstalledVersion:attributes[?key==`package_version`].value | [0]}' \
  --output table \
  --no-cli-pager
```

**Current assessment**

Several findings relate to execution paths that Homelab Sentinel does not appear to use, while Debian currently classifies some as minor, postponed or without an available stable-package fix. The Dockerfile and complete finding list will be reviewed before deciding whether to remediate, document as not applicable, or temporarily accept each critical finding.

**Verification required**

A final decision has not yet been made. Before ECS deployment:

1. Verify the base image and all packages installed by the Dockerfile.
2. Determine whether newer fixed packages or a newer base image are available.
3. Assess whether each critical vulnerability is reachable through the application.
4. Rebuild and rescan if changes are made.
5. Record any accepted risk and the controls limiting exposure.

### Additional High-severity finding after rebuild

**Finding:** `CVE-2026-86145`

**Package:** `pcre2 10.46-1~deb13u1`

**Severity:** High

**Cause:**

The refreshed Debian Trixie base image contains an affected PCRE2
package. The vulnerability can cause an out-of-bounds write when an
attacker-controlled regular expression is processed specifically through
the `pcre2_dfa_match()` API.

**Applicability assessment:**

Homelab Sentinel does not accept user-supplied regular expressions and
does not call `pcre2_dfa_match()`. Its API routes and status calculations
use fixed application-controlled values. No reachable exploitation path
was identified for the current application.

**Remediation:**

Upstream fixed the vulnerability in PCRE2 10.48. The container will be
rebuilt after the corrected package becomes available through the
maintained Python base image.

**Risk decision:**

Accepted for the temporary V0.2.0 learning deployment. Exposure will be
limited by non-root container execution, restricted security-group
ingress, absence of sensitive data and removal of the AWS resources after
testing.

## Lessons Learned

- The AWS root user and IAM administrator belong to the same AWS account and therefore return the same account ID, but their ARNs identify different principals.
- Temporary browser-based AWS CLI authentication avoids storing long-lived access keys in the development LXC.
- ECR stores versioned container images but does not run them; ECS will later retrieve and run the image.
- An image tag provides a readable version reference, while the digest identifies the exact image content.
- Enabling image scanning does not fix vulnerabilities automatically; the findings still need to be reviewed and addressed.
- An ECS service continuously reconciles its running tasks against its
  configured desired count.
- ECS replaces a stopped or unhealthy task rather than restarting the
  same task.
- Fargate task identities, ENIs and public IP addresses are ephemeral.
- Container health and persistent application state are separate
  concerns.
- Task replacement restores the application process but does not restore
  data held only in container memory.
- Stable routing and persistent state require infrastructure outside the
  individual task.
